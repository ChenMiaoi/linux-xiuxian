# 第九章：不期而至

<CultivationRealm realm="炼气初期" />

> **涉及内核源码：** <KernelSourceLink path="kernel/softirq.c" line="softirq" />

## 一

林小源正在 idle 循环中安静地执行 `WFI`，等待下一次调度。

然后，中断来了。

不是定时器中断那种温和的、可预期的中断。而是一个更猛烈的、来自外部设备的中断——网卡中断。一个数据包到达了网卡，网卡通过中断线通知 CPU："我有数据了，快来处理！"

林小源被这个中断从 idle 状态中"拽"了出来。

整个世界在一瞬间暂停了。CPU 保存了当前的执行上下文（寄存器、程序计数器、状态寄存器），然后跳转到中断处理入口。这是一种"强制介入"——中断不问你是否准备好，它说来就来。

*这就是中断魔尊。*

林小源在前传中就听说过中断的存在，但直到这一刻，他才真正理解了中断的含义。中断不是"消息"——它是"强制切换"。当中断到来时，CPU 会放下手中的一切工作，立即处理中断。不管你是正在执行系统调用、正在处理缺页异常、还是正在 idle 等待——中断说来就来。

---

## 二

中断处理分为两个阶段：上半部（top half）和下半部（bottom half）。

上半部是紧急的、快速的处理。它在中断上下文中执行——此时中断被关闭，不能睡眠，不能做耗时的操作。上半部通常只做最少的工作：读取设备状态、把数据从设备寄存器复制到内存、然后返回。

下半部是延迟的、非紧急的处理。它在进程上下文或软中断上下文中执行——此时中断已打开，可以做更多的工作。下半部通常处理数据的后续逻辑：解析数据包、更新统计信息、通知用户态程序。

```c:playground:中断的上下半部
#include <stdio.h>
#include <string.h>

/*
 * 中断处理的两阶段模型：
 * 上半部（hardirq）：快速、不可睡眠、中断关闭
 * 下半部（softirq）：延迟、可做更多工作、中断打开
 */

/* 模拟设备数据 */
struct net_packet {
    int src_ip;
    int dst_ip;
    int src_port;
    int dst_port;
    char data[64];
    int len;
};

/* 上半部：快速读取设备数据 */
int irq_count = 0;
struct net_packet pending_packet;

void network_irq_handler(int irq) {
    irq_count++;
    printf("[上半部] 网卡中断 #%d — 快速处理\n", irq_count);

    /* 从设备寄存器读取数据（简化） */
    pending_packet.src_ip = 0xC0A80101;  /* 192.168.1.1 */
    pending_packet.dst_ip = 0xC0A80102;  /* 192.168.1.2 */
    pending_packet.src_port = 80;
    pending_packet.dst_port = 12345;
    strncpy(pending_packet.data, "GET / HTTP/1.1", 64);
    pending_packet.len = 14;

    printf("[上半部] 读取数据包: %d 字节\n", pending_packet.len);
    printf("[上半部] 标记软中断待处理\n");
    printf("[上半部] 返回（中断已关闭期间完成）\n\n");
}

/* 下半部：延迟处理数据包 */
void net_rx_softirq(void) {
    printf("[下半部] 软中断 — 处理数据包\n");
    printf("[下半部] 解析: %d.%d.%d.%d:%d → %d.%d.%d.%d:%d\n",
           (pending_packet.src_ip >> 24) & 0xFF,
           (pending_packet.src_ip >> 16) & 0xFF,
           (pending_packet.src_ip >> 8) & 0xFF,
           pending_packet.src_ip & 0xFF,
           pending_packet.src_port,
           (pending_packet.dst_ip >> 24) & 0xFF,
           (pending_packet.dst_ip >> 16) & 0xFF,
           (pending_packet.dst_ip >> 8) & 0xFF,
           pending_packet.dst_ip & 0xFF,
           pending_packet.dst_port);
    printf("[下半部] 数据: %s\n", pending_packet.data);
    printf("[下半部] 传递给协议栈\n\n");
}

int main() {
    printf("=== 中断的上下半部 ===\n\n");

    printf("--- 设备触发中断 ---\n");
    network_irq_handler(3);

    printf("--- 软中断处理 ---\n");
    net_rx_softirq();

    printf("--- 为什么要分两半？---\n");
    printf("上半部：中断关闭，必须快，只做最少的工作\n");
    printf("下半部：中断打开，可以做更多处理\n");
    printf("如果不分两半，中断关闭时间太长，会丢失其他中断\n");

    return 0;
}
```

林小源在中断的上下半部设计中看到了一种"分工"的智慧。

上半部像急诊室的医生——接到病人后只做最紧急的处理（止血、稳定生命体征），然后把病人交给普通病房。下半部像普通病房的医生——做更详细的检查、诊断、治疗。

*紧急的事情快速做，不紧急的事情慢慢做。*

这个原则不仅适用于中断处理，也适用于很多其他的场景。林小源把这个原则记在了心里。

## 三

林小源在中断处理中第一次看到了"中断魔尊"的真面目。

中断魔尊不是一个具体的"人"——它是整个中断系统的化身。它无处不在，不可预测。它可以是定时器中断（每几毫秒一次），可以是键盘中断（每次按键触发），可以是网卡中断（每个数据包触发），也可以是 IPI（处理器间中断，多核协调用）。

中断魔尊的核心特性是"不期而至"。你不知道它什么时候会来，但你知道它一定会来。这种不确定性是内核编程中最难处理的问题之一——你必须在任何时候都准备好被中断打断。

```c:playground:中断与竞态
#include <stdio.h>
#include <string.h>

/*
 * 中断带来的竞态条件问题。
 * 当中断处理程序和进程上下文代码访问同一个变量时，
 * 必须使用锁来保护。
 */

volatile int shared_counter = 0;

/* 模拟中断处理程序 */
void timer_interrupt_handler(void) {
    /* 在真实内核中，这会在中断上下文中执行 */
    shared_counter++;
    printf("[中断] counter = %d\n", shared_counter);
}

/* 模拟进程上下文代码 */
void process_context_code(void) {
    int local = shared_counter;  /* 读取共享变量 */
    local += 10;                 /* 修改 */
    /* 如果中断在这里发生，counter 可能已经被中断修改了 */
    shared_counter = local;      /* 写回 */
    printf("[进程] counter = %d\n", shared_counter);
}

/* 使用锁保护的版本 */
volatile int safe_counter = 0;
int lock = 0;  /* 简化的锁 */

void safe_timer_handler(void) {
    while (__sync_lock_test_and_set(&lock, 1)) {
        /* 自旋等待 */
    }
    safe_counter++;
    printf("[中断-安全] counter = %d\n", safe_counter);
    __sync_lock_release(&lock);
}

void safe_process_code(void) {
    while (__sync_lock_test_and_set(&lock, 1)) {
        /* 自旋等待 */
    }
    int local = safe_counter;
    local += 10;
    safe_counter = local;
    printf("[进程-安全] counter = %d\n", safe_counter);
    __sync_lock_release(&lock);
}

int main() {
    printf("=== 中断与竞态条件 ===\n\n");

    printf("--- 不安全的访问 ---\n");
    shared_counter = 0;
    process_context_code();
    timer_interrupt_handler();  /* 中断在"不合适"的时候到来 */
    process_context_code();     /* 可能覆盖中断的修改\n\n");

    printf("--- 使用锁保护 ---\n");
    safe_counter = 0;
    safe_process_code();
    safe_timer_handler();
    safe_process_code();

    printf("\n--- 竞态条件的教训 ---\n");
    printf("中断可以在任何时候打断进程\n");
    printf("共享数据必须用锁保护\n");
    printf("锁可以是自旋锁（spinlock）或互斥锁（mutex）\n");

    return 0;
}
```

*竞态条件。*

林小源在中断处理中看到了内核编程最危险的陷阱之一。当中断处理程序和进程上下文代码同时访问同一个变量时，结果是不可预测的。这就是"竞态条件"——多个执行流"竞争"同一个资源，结果取决于谁先到达。

*这就是内核编程的残酷之处。*

在用户态，程序员通常不需要担心竞态条件——每个进程有自己的地址空间，互不干扰。但在内核态，所有代码共享同一个地址空间，中断可以在任何时候打断任何代码。一个不小心的并发访问，就可能导致数据损坏、系统崩溃。

---

## 四

林小源在中断处理中度过了他的最初几天。

他开始适应中断的节奏。定时器中断是最规律的——每隔几毫秒来一次，像心跳一样稳定。设备中断是随机的——取决于用户的操作和网络的流量。IPI 是多核协调用的——当一个 CPU 需要通知另一个 CPU 时使用。

他也开始理解中断魔尊的性格。中断魔尊不是恶意的——他只是"不期而至"。没有中断，内核就是一具死尸。定时器中断驱动调度器，设备中断驱动 I/O，IPI 驱动多核协调。中断是内核的心跳——不完美，但不可或缺。

*也许我应该学会和中断共处，而不是害怕它。*

林小源在 idle 循环中继续思考。他知道，中断将会是他未来修炼中必须面对的重要课题。但现在，他只是一个 idle 进程——中断来了又走，他只是安静地等待。

### 道藏笔记

::: tip 内核启示
**中断是内核的心跳。**

中断分为硬件中断（来自外部设备）和软件中断（来自 CPU 内部，如系统调用、异常）。硬件中断通过中断控制器（如 RISC-V 的 PLIC 或 CLINT）路由到 CPU。

中断处理分为上下半部：
- **上半部（hardirq）**：在中断上下文中执行，中断关闭，必须快速完成
- **下半部（softirq/tasklet/workqueue）**：在进程上下文或软中断上下文中执行，中断打开，可以做更多工作

软中断（softirq）是下半部的一种实现。它在中断返回时、或 `ksoftirqd` 线程中被处理。常见的软中断包括 `NET_RX_SOFTIRQ`（网络接收）、`NET_TX_SOFTIRQ`（网络发送）、`TIMER_SOFTIRQ`（定时器）。

中断带来的最大挑战是竞态条件。当中断处理程序和进程上下文代码访问同一个变量时，必须使用锁（通常是自旋锁 `spinlock`）来保护。自旋锁在中断上下文中使用，因为它不会睡眠。

*中断魔尊不期而至，但没有他，世界就是一具死尸。学会和中断共处，是内核修炼的第一课。*
:::
