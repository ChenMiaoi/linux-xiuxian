# 第十七章：task_struct 之躯

<CultivationRealm realm="筑基初期" />

> **涉及内核源码：** <KernelSourceLink path="include/linux/sched.h" line="task_struct" />

## 一

林小源决定先理解自己的"肉身"。

`task_struct` 是进程的身份证、户口本、病历、档案——所有关于一个进程的信息都记录在这里。他在前传中就看过 `task_struct` 的简化版本，但真正的 `task_struct` 有数百个字段，涵盖了一个进程从诞生到死亡的方方面面。

他开始逐字段地阅读。

调度相关的字段最先吸引了他的注意。`state` 是进程当前的状态——RUNNING、INTERRUPTIBLE、UNINTERRUPTIBLE、STOPPED、ZOMBIE。`prio` 是动态优先级，`static_prio` 是静态优先级。`policy` 是调度策略——SCHED_NORMAL、SCHED_FIFO、SCHED_RR。`se` 是调度实体，包含了 CFS 需要的 `vruntime` 和权重。

*这些字段决定了我什么时候能运行。*

身份信息也很重要。`pid` 是进程 ID，`tgid` 是线程组 ID（对于非线程进程，`tgid == pid`）。`comm` 是进程名，最多 15 个字符加上一个 `\0`。`real_parent` 指向创建这个进程的父进程，`parent` 指向当前的父进程（可能被 `ptrace` 修改）。`children` 是子进程链表，`sibling` 是兄弟进程链表。

*原来进程也有"家族关系"。*

```c:playground:task_struct 的身份字段
#include <stdio.h>
#include <stddef.h>

/* 简化的 task_struct 身份字段 */
struct task_identity {
    int pid;              /* 进程 ID */
    int tgid;             /* 线程组 ID */
    char comm[16];        /* 进程名 */
    int uid;              /* 用户 ID */
    int gid;              /* 组 ID */
    int euid;             /* 有效用户 ID */
    int egid;             /* 有效组 ID */
    int exit_state;       /* 退出状态 */
    int exit_code;        /* 退出码 */
};

int main() {
    struct task_identity bash = {
        .pid = 1234,
        .tgid = 1234,
        .uid = 1000,
        .gid = 1000,
        .euid = 1000,
        .egid = 1000,
        .exit_state = 0,
        .exit_code = 0,
    };
    __builtin_memcpy(bash.comm, "bash", 5);

    printf("=== task_struct 身份字段 ===\n\n");
    printf("进程名:    %s\n", bash.comm);
    printf("PID:       %d\n", bash.pid);
    printf("TGID:      %d\n", bash.tgid);
    printf("UID:       %d\n", bash.uid);
    printf("EUID:      %d\n", bash.euid);
    printf("GID:       %d\n", bash.gid);

    printf("\n--- uid vs euid ---\n");
    printf("uid  = 实际用户 ID（谁启动的进程）\n");
    printf("euid = 有效用户 ID（决定权限检查）\n");
    printf("当 setuid 程序运行时，euid != uid\n");
    printf("例如: passwd 命令 euid=0（root），uid=1000（普通用户）\n");

    return 0;
}
```

林小源在 `uid` 和 `euid` 的区别中看到了一种"权限委托"的机制。一个普通用户可以通过 `setuid` 程序临时获得 root 权限——程序以 root 的 `euid` 运行，但实际的 `uid` 仍然是普通用户。这是一种精妙的安全设计：最小权限原则。

## 二

内存管理相关的字段让林小源花了更多时间。

`mm` 指向 `mm_struct`——进程的地址空间描述符。`mm_struct` 包含了虚拟地址空间的布局：代码段的起始和结束地址、数据段的起始和结束地址、堆的起始地址、栈的起始地址。它还包含了页表的根指针（在 RISC-V 上是 `satp` 寄存器的值）和一个管理所有虚拟内存区域（VMA）的红黑树。

*原来地址空间是这样被管理的。*

文件相关的字段也很有趣。`files` 指向 `files_struct`，它包含了进程打开的所有文件描述符。每个文件描述符是一个整数索引，指向 `struct file` 的指针数组。`struct file` 包含了文件的当前位置（`f_pos`）、打开模式（`f_mode`）、以及指向 `file_operations` 的指针。

*文件描述符就是进程与外界沟通的桥梁。*

信号相关的字段是最后一批。`signal` 指向 `signal_struct`，它包含了信号队列、信号掩码、以及定时器。`sighand` 指向 `sighand_struct`，它包含了每个信号的处理函数。

林小源在 `task_struct` 中看到了一个进程的"全息图"——从身份到权限，从内存到文件，从信号到调度，所有信息都在这一个结构体中。

## 三

就在林小源研究 `task_struct` 的过程中，他注意到了一个有趣的现象。

kthreadd 婶婶——PID 2——在默默地创建内核线程。每隔一段时间，就会有一个新的内核线程被创建出来，执行某个特定的任务，然后在任务完成后睡眠。

林小源通过 `task_struct` 的 `comm` 字段看到了这些内核线程的名字：`kworker/0:0`、`ksoftirqd/0`、`rcu_preempt`、`watchdog`。每一个都有自己的职责，每一个都是 kthreadd 婶婶创建的。

*她就像一个沉默的工匠。*

kthreadd 婶婶不说话，不炫耀，不争抢 CPU 时间。她只是在需要的时候创建内核线程，然后继续她的等待。林小源从未听她说过一句话——她连 `comm` 字段都是固定的 "kthreadd"，从不改变。

但她的工作是不可或缺的。没有 kthreadd 婶婶，内核就无法创建内核线程。没有内核线程，软中断、RCU、工作队列等机制就无法运转。她是内核世界的"后勤部长"——不显眼，但不可或缺。

### 道藏笔记

::: tip 内核启示
**`task_struct` 是进程的"全息图"。**

它包含了进程的所有信息，可以分为几个大类：
1. **调度信息** — `state`、`prio`、`policy`、调度实体
2. **身份信息** — `pid`、`tgid`、`comm`、`uid`/`euid`/`gid`/`egid`
3. **家族关系** — `real_parent`、`parent`、`children`、`sibling`
4. **内存管理** — `mm_struct`（地址空间）、`active_mm`
5. **文件系统** — `files_struct`（打开的文件）、`fs_struct`（当前目录）
6. **信号** — `signal_struct`、`sighand_struct`
7. **安全** — `cred`（凭证）、`security`（LSM 安全模块数据）

`uid` 和 `euid` 的区别是权限管理的基础。`uid` 是实际用户 ID（谁启动的进程），`euid` 是有效用户 ID（决定权限检查）。`setuid` 程序可以让 `euid != uid`，从而临时提升权限。

*理解 task_struct，就是理解一个进程的全部。*
:::
