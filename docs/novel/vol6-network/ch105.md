# 第一百零五章：第一枚报文

<CultivationRealm realm="问道期" />

> **涉及内核源码：** <KernelSourceLink path="include/linux/skbuff.h" line="struct sk_buff" />

## 一

第一枚报文不是从海里来的，而是从一段用户缓冲区里醒来。

林小源把手放在刚领到的 fd 上，听见用户态传来一句轻轻的 `send()`。那声音穿过 VFS 的桥，找到 socket，再沿着 `proto_ops` 进入协议族的发送路径。码头工人从用户缓冲区取出货物，准备把它装进真正能在内核网络栈里流转的载体。

"这时还不是 `sk_buff` 吗？"林小源问。

"用户态给的是字节。"小吏说，"协议栈需要的是带元数据的报文对象。等它进入内核网络路径，就会被组织成 `struct sk_buff`。你可以先把它看成一封会不断加信封的信。"

远处，一张空白羊皮纸被展开。纸边标着 `head`、`data`、`tail`、`end`，但细节还藏在雾中。

"第百一十一章会专门讲它。"小吏说，"现在只看第一眼：没有 sk_buff，协议栈就没有可以传递的报文肉身。"

## 二

报文开始下潜。

第一层给它加上运输层的封皮，第二层加上网络层的地址，第三层还会加上链路层的外衣。每一层都不想反复搬动整批货物，于是只调整指针、预留头部空间、记录校验和状态与设备去向。

林小源看见那张羊皮纸不是单纯的数据块，而是一套"数据加说明书"。它既带着 payload，也带着路由、协议、设备、socket、校验和、队列位置等信息。真正的网络栈不是把字节一路复制到底，而是在对象上不断更新视角。

"这就是为什么后面要单独学 sk_buff。"小吏说，"不懂它，就看不懂收包、发包、NAPI、offload、netfilter、XDP 与设备驱动之间的协作。"

## 三

第一枚报文被送到海边时，天色正暗。

它还没有经历 TCP 握手，没有穿过路由，没有进入 NAPI，也没有被 netfilter 审问。可林小源已经看见它未来的路：socket 是入口，协议族决定航线，netns 决定海域，sk_buff 成为肉身，网络设备负责真正出海。

海关小吏把最后一枚印章盖在通行文书上。

"你已经走完入海前的五道门。"他说，"从下一章开始，你可以真正望海了。"

林小源回头望去，永恒之森仍在身后，VFS 的桥还在雾中若隐若现。他终于明白，内核子系统之间没有绝对的断崖。文件系统的 fd、进程的 namespace、网络的 socket，在边界处彼此交错。

然后，他向海岸走去。

### 道藏笔记

::: tip 内核启示
网络发送路径从用户缓冲区和 fd 开始，经过 socket、协议族操作表与网络命名空间，最终进入以 `sk_buff` 为核心的报文流转体系。

`sk_buff` 不只是 payload，它是报文数据和大量元数据的组合。后续 NAPI、netfilter、路由、offload、驱动发送接收都会围绕它展开。本章只做铺垫，详细结构留给 `sk_buff` 专章。
:::
