# 第一百零一章：文件尽头是 socket

<CultivationRealm realm="问道期" />

> **涉及内核源码：** <KernelSourceLink path="net/socket.c" line="sock_map_fd" />

## 一

林小源以为自己已经离开了文件系统，脚下却仍然踩着一块刻着 `file` 的石板。

VFS 没有立刻放他走。老者站在永恒之森的尽头，指着前方的海雾："你以为网络从海开始？错。对用户态来说，网络先从文件描述符开始。"

"socket 也是文件？"林小源皱眉。

"不是普通磁盘文件。"VFS 说，"但它会被安装进进程的 fd table。用户态拿到的仍然是一个整数 fd，`read()`、`write()`、`poll()`、`close()` 这些熟悉的手势仍然能摸到它。只是 fd 背后不再是 inode 上的数据块，而是一只 `struct socket`，再往下才是协议栈。"

林小源低头看去，石板下方有一条窄桥伸向海边。桥的一端写着 `struct file`，另一端写着 `struct socket`。桥中央刻着一个名字：`sock_map_fd()`。

"这是文件系统和网络栈的第一处接缝。"VFS 说，"网络不是绕开 VFS 另开天道，而是借 fd 这套用户态契约入世。"

## 二

林小源沿桥前行，发现桥面并不平坦。

普通文件的 `file_operations` 像林中旧路，`read_iter`、`write_iter`、`llseek` 各有归处。socket 的路却更像一座潮汐码头：`sendmsg`、`recvmsg`、`poll`、`ioctl`、`release`，每一个动作都要绕到网络对象上。

"所以 `close(fd)` 关掉的不只是一个数字。"林小源说。

"对。"VFS 回答，"关闭 fd 会释放 `struct file` 的引用，进一步走到 socket release。一个 fd 可以被 `dup()` 复制，多个 fd 可以指向同一个打开文件对象；socket 的生命周期也要受引用计数约束。你在用户态看到的是一个整数，内核里看到的是一串对象引用。"

海雾中传来轻微的链响。林小源听见 `files_struct`、`fdtable`、`file`、`socket` 依次回应，像不同山门的令牌互相验证。

"文件系统教你的第一课，在这里仍然成立。"VFS 说，"名字、对象、打开状态要分清；fd、file、socket 也不能混为一谈。"

## 三

桥尽头站着一位海关小吏，手里捧着一枚刚铸好的 fd。

"想入海，先领牌。"小吏说，"但牌子不是船。牌子只是让进程以后能找到那只船。"

林小源接过 fd，看见上面同时映出两层影子：上层是 VFS 的文件表，下层是网络栈的 socket。一个进程调用 `socket()`，内核先创建 socket 对象，再把它包装成 file，最后把 file 放进 fd table。之后用户态用这个 fd 调 `bind()`、`connect()`、`send()`、`recv()`，内核才能顺藤摸瓜找到真正的网络对象。

这时，远方海面隐隐亮起。

VFS 的声音从身后传来："记住这座桥。你将来调试网络泄漏、连接悬挂、epoll 异常时，都会回到这里。socket 的故事从海开始，但它的用户态入口，仍然是 fd。"

### 道藏笔记

::: tip 内核启示
socket 是网络通信端点，但用户态通常通过文件描述符使用它。`socket()` 创建内核 socket 对象后，会把它安装成一个 fd；后续 `close()`、`poll()`、`send()`、`recv()` 等操作都从 fd 找回内核对象。

这就是 VFS 与网络栈的关键接口：fd 是用户态契约，`struct file` 是打开对象，`struct socket` 才是网络端点。不要把 fd、file、socket 写成同一件事。
:::
