# 第五十二章：调度延迟

<CultivationRealm realm="结丹圆满" />

> **涉及内核源码：** <KernelSourceLink path="kernel/sched/fair.c" line="wakeup_preempt_entity" />

## 一

林小源在研究调度器的过程中，发现了一个关键的性能指标：调度延迟。

调度延迟是指从进程变为可运行到它实际获得 CPU 的时间。这个延迟越短，系统的响应性越好。

```c:playground:调度延迟 — 响应性的度量
#include <stdio.h>

/*
 * 调度延迟的来源：
 *
 * 1. 调度器本身的开销
 *    pick_next_task() + context_switch()
 *    通常 1-10 微秒
 *
 * 2. 当前进程的时间片未用完
 *    需要等到时钟中断或进程主动让出
 *    通常 0-6 毫秒
 *
 * 3. 更高优先级的进程在运行
 *    需要等到高优先级进程让出 CPU
 *    不确定
 *
 * 4. CPU 亲和性限制
 *    亲和的 CPU 都在忙
 *    需要等待负载均衡
 *
 * 优化调度延迟的方法：
 *   - 唤醒抢占（wake-up preemption）
 *   - 减小时间片
 *   - 提高进程优先级
 *   - 绑定到空闲的 CPU
 */

struct latency_source {
    const char *name;
    unsigned long typical_ns;
    unsigned long worst_ns;
};

int main() {
    printf("=== 调度延迟 ===\n\n");

    struct latency_source sources[] = {
        { "调度器开销",          5000,     20000 },
        { "时间片等待",        300000,   6000000 },
        { "高优先级进程运行", 1000000, 100000000 },
        { "CPU 亲和性限制",   100000,   1000000 },
    };
    int nr = sizeof(sources) / sizeof(sources[0]);

    printf("调度延迟的来源：\n");
    printf("%-20s %-15s %-15s\n", "来源", "典型延迟", "最坏延迟");
    printf("%-20s %-15s %-15s\n", "---", "---", "---");

    for (int i = 0; i < nr; i++) {
        printf("%-20s %-12.2f ms %-12.2f ms\n",
               sources[i].name,
               sources[i].typical_ns / 1000000.0,
               sources[i].worst_ns / 1000000.0);
    }

    printf("\n--- 唤醒抢占 ---\n");
    printf("当一个进程从睡眠中醒来时：\n");
    printf("  1. 计算醒来的进程是否应该抢占当前进程\n");
    printf("  2. 如果是，设置 TIF_NEED_RESCHED\n");
    printf("  3. 当前进程被抢占\n");
    printf("  4. 醒来的进程立即获得 CPU\n\n");
    printf("唤醒抢占的条件：\n");
    printf("  醒来进程的 vruntime < 当前进程的 vruntime - 候补阈值\n");
    printf("  这保证了交互式进程的低延迟\n");

    printf("\n--- 延迟敏感的应用 ---\n");
    printf("音频处理: 延迟 < 10ms\n");
    printf("视频播放: 延迟 < 33ms\n");
    printf("网络服务器: 延迟 < 1ms\n");
    printf("交互式应用: 延迟 < 100ms\n");

    return 0;
}
```

*原来"延迟"是调度器的"敌人"。*

---

## 二

林小源在研究调度延迟的过程中，理解了唤醒抢占的重要性。

唤醒抢占是降低调度延迟的关键机制。当一个交互式进程（如 shell、编辑器）从睡眠中醒来时，它需要立即获得 CPU——否则用户会感到"卡顿"。

*原来"唤醒"是"响应"的关键。*

林小源还发现了一个权衡：唤醒抢占可以降低延迟，但也会增加上下文切换的频率。如果唤醒抢占太激进，频繁的上下文切换反而会降低吞吐量。

*原来"优化"也是"权衡"。*

---

## 三

林小源在观察调度延迟的过程中，理解了不同应用对延迟的不同需求。

音频处理需要极低的延迟（< 10ms），否则会出现杂音。视频播放需要中等延迟（< 33ms），否则会掉帧。交互式应用需要较低延迟（< 100ms），否则会感觉卡顿。

*原来"需求"是"设计"的驱动力。*

---

### 道藏笔记

::: tip 内核启示
**调度延迟是进程从变为可运行到实际获得 CPU 的时间。**

调度延迟的来源：
1. 调度器本身的开销（~5μs）
2. 当前进程的时间片未用完（~3ms）
3. 更高优先级的进程在运行（不确定）
4. CPU 亲和性限制（~100μs）

降低调度延迟的方法：
- 唤醒抢占 — 醒来的进程可以抢占当前进程
- 减小时间片 — 减少等待时间
- 提高进程优先级 — 更容易被选中
- 绑定到空闲的 CPU — 避免等待

唤醒抢占的条件：
- 醒来进程的 `vruntime` < 当前进程的 `vruntime` - 候补阈值
- 保证交互式进程的低延迟

*调度延迟是"响应性"的度量——越低越好。*
:::
